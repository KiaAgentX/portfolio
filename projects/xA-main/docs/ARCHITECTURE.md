# میز هرمس (Hermes Desk)
## پیشخوان عملیات هوش مصنوعی با تأیید انسان

نسخه: 0.1 — طرح پخته‌شده از ایده خام  
تاریخ: ۲۰۲۶-۰۹-۰۲  
وضعیت: طرح معماری برای تصمیم‌گیری، هنوز محصول نهایی نیست

---

## ۱. ایده خام چه بود، و چه چیزی کم داشت

ایده خام این بود:

> مشتری از تلگرام / واتساپ / ایمیل پیام بدهد → هرمس پردازش کند → چند ایجنت متخصص جواب بسازند → آدمین در پنل و تلگرام‌وب‌اپ تأیید کند → روی Railway بالا بیاید → اسناد شرکت روی دیسک Railway نماند و بعد از اتمام تسک به حافظهٔ جانبی سالانه برود.

این یک **موتور** است، نه یک کسب‌وکار. چهار جای خالی دارد:

1. **عمودی (vertical)** مشخص نیست. پشتیبانی؟ حسابداری؟ حقوقی؟ فروش؟ پذیرش کلینیک؟ بدون گوهٔ اول، محصول به «چت‌بات همه‌کاره» تبدیل می‌شود و می‌میرد.
2. **مشتری نباید مستقیم با مغز هرمس حرف بزند.** هرمس ابزار شل، فایل و وب دارد. اگر یوزر عمومی به گیت‌وی هرمس وصل شود، جیلبریک و سوءاستفاده تقریباً قطعی است.
3. **تأیید هرمس (`/approve`) تأیید محصول نیست.** آن برای دستور خطرناک شل است، نه برای «این جواب برود برای مشتری» یا «این فاکتور صادر شود».
4. **دیسک Railway سیستم ثبت اسناد نیست.** هم برای امنیت شرکت‌ها ضعیف است، هم برای ده ترابایت در ده سال از نظر هزینه و قابلیت (لایف‌سایکل، Object Lock، نسخه‌بندی) مناسب نیست.

محصول واقعی این است:

> مشتری روی کانالی که از قبل استفاده می‌کند پیام می‌دهد. یک پیشخوان تیکت می‌سازد. هرمس با ایجنت‌های متخصص پیش‌نویس کار را آماده می‌کند. یک انسان امضا می‌کند. بعد عملیات اجرا می‌شود. بعد همه‌چیز به‌صورت رمزنگاری‌شده و غیرقابل‌تغییر بایگانی می‌شود.

نام داخلی پیشنهادی: **Hermes Desk / میز هرمس**  
دسته‌بندی: *Human-gated AI operations desk*

## ۲. قانون‌های محصول (غیرقابل‌مذاکره)

1. **Ingress گنگ است، مغز پشت دیوار است.** بات مشتری فقط پیام را می‌گیرد و تیکت می‌سازد. هرمس به اینترنت مشتری وصل نیست.
2. **هیچ خروجی‌ای بدون امضای انسان به دنیای بیرون نمی‌رود** — مگر در allowlist خیلی محدود (مثلاً «پیام دریافت شد»).
3. **هرمس کارگر است، محصول نیست.** محصول = تیکت + مسیریاب + دروازهٔ تأیید + خزانهٔ اسناد + لاگ حسابرسی.
4. **Volume فقط حافظهٔ کاری است.** اسناد شرکت، پیوست‌ها، خروجی نهایی، و آرشیو ده ساله فقط در Object Storage رمزنگاری‌شده.
5. **واتساپ فقط Cloud API رسمی.** Baileys / نشست شخصی برای محصول تجاری یعنی ریسک بن و نقض ToS متا.
6. **YOLO خاموش و قفل‌شده در سطح پالیسی، نه سشن.** پنل هرمس هرگز پابلیک نباشد.
7. **چندمستأجری از روز اول در داده.** حتی اگر v1 تک‌شرکتی باشد، `tenant_id` روی هر ردیف و هر آبجکت باشد.

## ۴. سرویس‌ها روی Railway

یک پروژه Railway با محیط‌های `dev` / `staging` / `prod`.

| سرویس | نقش | دیسک |
|---|---|---|
| `ingress` | وب‌هوک تلگرام، واتساپ، inbound ایمیل | ندارد |
| `api` | Control Plane (FastAPI یا Nest) | ندارد |
| `web` | پنل آدمین + همان باندل Telegram Mini App | ندارد |
| `hermes` | گیت‌وی/ورکر هرمس، worker-only | Volume کوچک روی `/data` (۵–۲۰ گیگ) |
| `postgres` | تیکت، کاربر، تأیید، حسابرسی | Volume دیتابیس |
| `redis` | صف، قفل، pub/sub هشدار | Volume کوچک یا ephemeral |
| *(خارج از Railway)* Vault | اسناد و آرشیو | Object storage |

لینک قالب کاربر (`nous-workshop/nous-hermes-railway-template`) **وجود ندارد (۴۰۴)**. مبدأ درست:

- هسته: [NousResearch/hermes-agent](https://github.com/NousResearch/hermes-agent)
- قالب Railway آماده: `lovexbytes/hermes-railway-template` یا ایمیج رسمی `nousresearch/hermes-agent`

هرمس را به‌عنوان **ورکر داخلی** دیپلوی کن، نه بات عمومی. مشتری به `ingress` وصل می‌شود، نه به گیت‌وی هرمس.

اتصال مدل: هرمس از روز اول OpenAI-compatible است.

```text
HERMES_INFERENCE_PROVIDER=openai_compat
OPENAI_BASE_URL=https://openrouter.ai/api/v1
OPENAI_API_KEY=...
# یا هر vLLM / LiteLLM / Together / Groq / سازگار دیگر
```

`HERMES_GIT_REF` را پین کن (مثلاً `v2026.7.7.2`). داخل کانتینر `hermes update` نزن.

## ۵. جریان یک پیام (Happy path)

1. مشتری در واتساپ می‌نویسد: «فاکتور سفارش ۱۲۴ را با اصلاح آدرس بفرستید» + عکس کارت ملی.
2. `ingress` پیام را نرمال می‌کند:
   ```json
   {
     "tenant_id": "acme",
     "channel": "whatsapp",
     "external_user_id": "3161xxxxxxx",
     "thread_id": "...",
     "text": "...",
     "attachments": ["vault://acme/inbound/2026/09/02/..."]
   }
   ```
3. پیوست **قبل از رسیدن به مدل** به Vault می‌رود (رمزنگاری پاکت). روی Volume هرمس کپی نمی‌ماند.
4. Control Plane تیکت `TCK-1842` می‌سازد. وضعیت: `received`.
5. ACK کانال: «پیامتان ثبت شد. شماره پیگیری TCK-1842.»
6. مسیریاب (مدل کوچک + قوانین) تخصص را مشخص می‌کند: `accounting` + نیاز به `kyc_check`.
7. صف Redis جاب را به هرمس می‌دهد. هرمس با پروفایل‌های Bot Mode حلقه می‌زند:
   - `intake` هویت و موجودیت‌ها را استخراج می‌کند
   - `accounting` پیش‌نویس فاکتور و ایمیل را می‌سازد
   - `compliance` ریسک را نمره می‌دهد
8. خروجی هرمس **پیش‌نویس** است، نه ارسال:
   ```json
   {
     "ticket_id": "TCK-1842",
     "proposed_actions": [
       {"type": "send_whatsapp", "text": "..."},
       {"type": "issue_invoice", "payload": {...}}
     ],
     "rationale": "...",
     "risk": "medium",
     "citations": ["vault://..."]
   }
   ```
9. وضعیت تیکت: `awaiting_approval`. آلرت به آدمین‌ها:
   - نوتیف تلگرام با دکمهٔ باز شدن Mini App
   - ردیف در پنل وب
10. آدمین در Mini App: پیش‌نویس را می‌بیند، متن را ویرایش می‌کند، Approve می‌زند. امضا با `admin_id` + زمان + هش پیش‌نویس در audit می‌نشیند.
11. Control Plane اکشن‌ها را اجرا می‌کند (خودش، نه هرمس).
12. هرمس بستهٔ نهایی را به Vault می‌فرستد: ورودی، خروجی، rational، امضا، هش‌ها. وضعیت: `archived`.
13. روی Volume هرمس فقط ایندکس سشن کاری می‌ماند و بعد از N روز پاک می‌شود.

اگر آدمین Reject کند: تیکت برمی‌گردد به هرمس با کامنت انسان. سقف حلقه مثلاً ۳ دور، بعد escalate به انسان خالص.

## ۶. ایجنت‌های متخصص — چطور طراحی شوند

هرمس **Bot Mode** دارد: هر بات = یک پروفایل جدا (`~/.hermes/profiles/<name>/`) با SOUL.md، مهارت، تولست، مدل و حافظهٔ خودش. **برای هر حرفه یک سرویس Railway جدا نساز.** یک runtime هرمس + چند پروفایل.

پیشنهاد فهرست v1 (حداکثر ۵؛ بیشتر از این در شروع یعنی هیچ‌کدام خوب کار نمی‌کنند):

| بات | شغل | ابزار مجاز | خروجی |
|---|---|---|---|
| `intake` | منشی | هیچ ابزار خارجی | تیکت ساخت‌یافته |
| `support` | پشتیبانی | دانش‌نامهٔ Vault (خواندنی) | پیش‌نویس جواب |
| `sales` | فروش | CRM خواندنی | کوالیفای + پیش‌نویس پیشنهاد |
| `accounting` | حسابداری | صدور سند فقط به‌صورت پیش‌نویس | فاکتور پیشنهادی |
| `compliance` | ناظر | بدون ارسال | نمرهٔ ریسک، پرچم PII/جیلبریک |

قوانین متخصص‌ها:

- هر بات **حداقل ابزار** را دارد. حسابداری شل ندارد. پشتیبانی وب آزاد ندارد.
- حافظهٔ بات سازمانی است نه شخصیِ مشتری. پروفایل مشتری در Postgres است.
- مهارت‌ها (`SKILL.md`) رویه‌های شرکت‌اند: «چطور مرجوعی را رسیدگی کنیم»، نه دانش مدل.
- مدل‌ها را جدا پین کن: intake مدل ارزان، accounting مدل قوی‌تر، compliance مدل سخت‌گیر.
- حلقه را خودت ارکستر کن (گراف مشخص)، نه «چند ایجنت با هم حرف بزنند تا درست شود». هرمس Bot Mode group-chat دارد؛ برای محصول مشتری‌دار خطرناک و غیرقابل‌حسابرسی است.

گراف پیشنهادی v1:

```
intake → (router) → specialist → compliance → HITL
```

نه لوپ آزاد. اگر compliance رد کرد، یک بار برگشت به specialist با دلیل. بار دوم = انسان.

## ۷. دروازهٔ تأیید (قلب محصول)

دو سطح تأیید را قاطی نکن:

| سطح | چیست | کجا |
|---|---|---|
| A | دستور خطرناک شل هرمس | داخل هرمس، `approvals.mode: manual`، YOLO ممنوع |
| B | تأیید کسب‌وکاری خروجی | Control Plane + Mini App + پنل |

سطح B را خودت بساز. UX آدمین در Telegram Mini App:

- لیست تیکت‌های `awaiting_approval`
- اصل پیام مشتری + پیوست‌ها
- پیش‌نویس جواب / عملیات
- دلیل هرمس و نمرهٔ ریسک
- دکمه‌ها: تأیید / ویرایش و تأیید / رد با دلیل / واگذاری
- برای ریسک بالا: تأیید دو نفره (maker-checker)

هشدار باید به **گروه آدمین تلگرام** و پنل برسد، نه فقط یک نفر. Timeout مثلاً ۳۰ دقیقه؛ بعد escalate. Fail-closed: بدون امضا هیچ ارسال/عملیاتی نیست.

Mini App همان فرانت `web` است که با `initData` تلگرام احراز می‌شود. یک کدبیس، دو پوسته.

## ۸. حافظهٔ جانبی — طرح درست برای ۱۰ سال و ده‌ها ترابایت

نگرانی «دیسک Railway برای اسناد شرکت امن نیست» درست است، اما راه‌حل «یک دیسک بغلش بگذاریم» غلط است.

### چرا Volume راه‌حل نیست

- برای بلوک‌استوریج اپ است، نه آرشیو اشیاء.
- گران‌تر از آبجکت استوریج (حدود ۰.۱۵ دلار/گیگ/ماه در برابر ۰.۰۱۵).
- سقف پلن‌ها برای ده‌ها ترابایت عملی نیست.
- نسخه‌بندی، Object Lock، لایف‌سایکل، WORM ندارد.
- رمزنگاری در سطح دیسک زیرساخت است، نه per-object و نه کلید دست خودت.
- بک‌آپ و خروج از قفل فروشنده سخت است.

Volume فقط برای:

- `~/.hermes` (کانفیگ، سشن کاری، مهارت)
- Postgres / Redis

و باید فرض کنی **از بین می‌رود**. هر حقیقتی که باید بماند، قبل از اتمام جاب در Vault است.

### Vault پیشنهادی

برای محصول EU (GDPR، موقعیت فعلی هلند):

**توصیهٔ اصلی:** Cloudflare R2 در منطقهٔ EU + رمزنگاری سمت کلاینت.  
**جایگزین compliance-heavy:** AWS S3 در `eu-central-1` یا `eu-west-1` با SSE-KMS + Object Lock (WORM) + Intelligent-Tiering.  
**Railway Buckets:** برای پیش‌نویس و dev خوب است (S3-سازگار، ۰.۰۱۵ دلار/گیگ، egress رایگان) ولی **هنوز ندارد:** server-side encryption، versioning، object lock، lifecycle. برای آرشیو ۱۰سالهٔ اسناد شرکت انتخاب نهایی نباشد.

لایهٔ رمزنگاری اجباری (چون حتی R2/S3 را کاملاً امین حساب نکن):

```
plaintext → DEK تصادفی → AES-256-GCM
DEK با KEK (از KMS یا age/libsodium) قفل می‌شود
در Vault فقط ciphertext + encrypted DEK + hash می‌رود
```

کلید هر tenant جدا. Railway فقط ciphertext می‌بیند.

طرح کلید:

```
vault://{tenant}/{year}/{month}/{ticket_id}/{sha256}
```

متادیتا در Postgres (قابل جستجو)، فایل در Vault (قابل مقیاس).

### لایف‌سایکل ۱۰ ساله

Railway Buckets لایف‌سایکل ندارد؛ پس Vault نهایی باید داشته باشد:

| سن | کلاس | مثال |
|---|---|---|
| ۰–۹۰ روز | Hot | R2 Standard / S3 Standard |
| ۹۰ روز–۱۸ ماه | Warm | R2 + دسترسی کمتر / S3 Standard-IA |
| ۱۸ ماه–۱۰ سال | Cold | S3 Glacier Instant Retrieval یا Deep Archive |
| بعد از ۱۰ سال | حذف یا نگه به استناد قانونی | با رکورد حذف در audit |

هزینهٔ خام نگهداری (فقط استوریج، بدون egress):

| حجم | R2 / Railway Bucket | S3 Standard | Glacier Deep Archive |
|---|---|---|---|
| ۱۰۰ گیگ | ~۱.۵ دلار/ماه | ~۲.۳ | ~۰.۱ |
| ۱ ترابایت | ~۱۵ | ~۲۳ | ~۱ |
| ۱۰ ترابایت | ~۱۵۰ | ~۲۳۰ | ~۱۰ |
| ۵۰ ترابایت | ~۷۵۰ | ~۱۱۵۰ | ~۵۰ |

پس «ده‌ها ترابایت در ده سال» شدنی است، **اگر** فایل خام روی Volume نماند و cold archive داشته باشی. اگر همه چیز ۱۰ سال Hot بماند، هزینه محصول را می‌کشد.

قانون هرمس بعد از تسک:

1. بستهٔ نهایی را بساز (ورودی، خروجی، امضا، هش).
2. به Vault بفرست و `etag`/هش را در تیکت بنویس.
3. کپی کاری روی `/data` را پاک کن.
4. اگر آپلود شکست، تیکت `archive_failed` بماند و آلرت بدهد — موفقیت دروغین ممنوع.

## ۹. داده و حسابرسی

### Postgres (منبع حقیقت عملیاتی)

- `tenants`
- `users` / `identities` (نگاشت تلگرام/واتساپ/ایمیل)
- `tickets` + `ticket_events` (append-only)
- `approvals` (چه کسی، چه هشی، چه تغییری)
- `agent_runs` (کدام بات، کدام مدل، توکن، هزینه)
- `objects` (اشاره‌گر به Vault)

### Redis

- صف جاب (`intake`, `agent`, `send`, `archive`)
- قفل تیکت (یک ران در لحظه)
- fanout هشدار

### Audit

هر رویداد: `who / what / when / before_hash / after_hash`.  
لاگ حسابرسی append-only است و علاوه بر Postgres به Vault هم mirror می‌شود. این همان چیزی است که مشتری سازمانی می‌خرد، نه خود چت.

## ۱۰. امنیت — چون این محصول با اسناد شرکت بازی می‌کند

1. گیت‌وی هرمس و داشبوردش **پابلیک نباشند.** فقط شبکهٔ خصوصی Railway + SSH.
2. `approvals.mode: manual` روی هرمس. `HERMES_YOLO_MODE` در محیط ست نشود. `/yolo` را در پروفایل محصول disable کن. (سابقه: ایجنت هرمس در حالت YOLO برای شناسایی روی زیرساخت دولتی استفاده شده.)
3. مشتری allowlist هرمس نیست؛ اصلاً به هرمس وصل نیست.
4. پرامپت اینجکشن: پیوست و متن مشتری همیشه untrusted. compliance قبل از HITL اجرا شود.
5. PII: کارت ملی و قرارداد در Vault رمزنگاری‌شده؛ در پرامپت فقط ارجاع `vault://...` مگر آدمین صریحاً باز کند.
6. GDPR (هلند / اتحادیه اروپا):
   - داده در منطقهٔ EU
   - مبنای قانونی نگهداری ۱۰ ساله را بنویس (قرارداد یا الزام قانونی). با حق فراموشی در تضاد است مگر استثنا.
   - DPA با Railway و ارائه‌دهندهٔ Vault
   - ثبت پردازش (RoPA)
7. واتساپ: Business API + webhook verify + قالب پیام خارج از پنجرهٔ ۲۴ ساعته.
8. اسرار فقط Railway Variables / secret store. هیچ کلید روی Volume.

## ۱۲. فازبندی — از خام به قابل‌فروش

### فاز ۰ — دو هفته: اسپایک
یک کانال (تلگرام)، یک متخصص (`support`)، HITL در پنل وب ساده، Vault روی R2، هرمس روی Railway به‌صورت داخلی. هدف: یک تیکت واقعی از پیام تا تأیید تا بایگانی.

### فاز ۱ — MVP قابل‌فروش (۶–۸ هفته)
- تلگرام + ایمیل
- Mini App تأیید
- ۳ بات: intake / support / compliance
- Postgres + Redis + R2
- audit ساده
- یک مشتری پایلوت (ترجیحاً خودت یا یک شرکت آشنا)

### فاز ۲ — کانال پول‌ساز
- WhatsApp Cloud API
- maker-checker برای ریسک بالا
- دانش‌نامهٔ شرکت در Vault + RAG محدود
- گزارش هزینهٔ توکن per ticket

### فاز ۳ — مقیاس ۱۰ ساله
- لایف‌سایکل Hot/Warm/Cold
- Object Lock
- چندمستأجری
- خروج از قفل: export کامل تیکت+اسناد

معیار ورود به فاز بعد: فاز قبل با تیکت واقعی، نه دموی شاد.

## ۱۴. ریسک‌هایی که ایدهٔ خام ندیده

1. **جیلبریک مشتری** اگر هرمس مستقیم پاسخ بدهد.
2. **بن واتساپ** با نشست غیررسمی.
3. **قفل فروشنده روی Volume** وقتی ۱۰ ترابایت شدی و می‌خواهی جابه‌جا شوی.
4. **حق فراموشی GDPR در برابر نگهداری ۱۰ ساله.**
5. **هزینهٔ توکن در لوپ چندایجنتی** — بدون سقف جاب، قبض می‌ترکد.
6. **آدمین گلوگاه می‌شود.** اگر هر پیام نیاز به انسان داشته باشد، محصول مقیاس ندارد. راه‌حل: بعد از پایلوت، allowlist جواب‌های کم‌ریسک، نه حذف دروازه از روز اول.
7. **قالب Railway عمومی ≠ محصول تو.** فقط موتور را بالا می‌آورد.

---

## ۱۵. تصمیم‌هایی که قبل از کد باید گرفته شوند

1. این را برای **شرکت خودت** می‌سازی یا **SaaS برای دیگران**؟
2. گوهٔ اول کدام است: پشتیبانی، حسابداری/فاکتور، حقوقی/قرارداد، نوبت‌دهی، فروش؟
3. اولین کانال: تلگرام (سریع و رایگان) یا واتساپ (جایی که مشتری ایرانی/اروپایی واقعاً هست)؟
4. آیا نگهداری ۱۰ ساله الزام قانونی است یا «شاید لازم شد»؟ این Vault را عوض می‌کند.
5. آدمین یک نفر است یا شیفت چندنفره؟

تا شمارهٔ ۲ جواب نداشته باشد، ایجنت متخصص طراحی نکن.

## ۱۶. جملهٔ پختهٔ محصول

> میز هرمس یک پیشخوان عملیات است که پیام مشتری را از تلگرام، واتساپ و ایمیل به تیکت تبدیل می‌کند، با مغز هرمس و ایجنت‌های متخصص پیش‌نویس کار را می‌سازد، فقط بعد از امضای انسان اجرا می‌کند، و اسناد را بیرون از دیسک Railway در خزانهٔ رمزنگاری‌شده با نگهداری سالانه می‌گذارد.

اگر این جمله برای یک عمودی مشخص (مثلاً «برای دفاتر حسابداری SME در هلند») صادق باشد، ایده پخته است. اگر هنوز «برای همه» است، هنوز خام است — ولی معماری‌اش دیگر خام نیست.
